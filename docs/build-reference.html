How Star Player of the Week is built

Owner-only
Living document

A working reference for presenting this app with full command of the details — the stack, the data model, the security model, and how a change actually reaches production. Updated as the app changes.

01 The stack

Frontend

React + TypeScript

Built with Vite. UI styled with Tailwind CSS on a small custom token system (colors, spacing, type scale) rather than a component library's defaults.

Backend

Firebase

No custom server. Firebase Authentication handles sign-in (email + password); Cloud Firestore is the database.

Database

Cloud Firestore

A NoSQL document database — data lives in named "collections" of JSON-like documents, not SQL tables. Real-time by default: the app subscribes to live updates instead of polling.

Hosting

Firebase Hosting

Static site hosting on Google's CDN, deployed straight from the command line. No separate server to patch or scale.

UI primitives

Radix UI + custom

Accessible dialog/toast primitives from Radix; everything else (buttons, fields, badges) is a small hand-built component set matching the brand.

Typography

Fraunces · Inter · JetBrains Mono

Self-hosted via @fontsource — no third-party font requests at runtime.

Testing

Vitest + Firestore emulator

Unit tests for pure logic, plus a dedicated suite that runs the actual security rules against a local Firestore emulator to prove access control, not just UI behavior.

Source control

GitHub

Single main branch. Every change ships as a commit before it deploys.

02 How a request flows through it

Browser

React app

Vite build

Identity

Firebase Auth

email + password

Data

Firestore

real-time listeners

Enforced by

Security Rules

server-side, not the app

There is no backend server the app talks to for permissions — the client reads and writes Firestore directly, and Firestore Security Rules (a separate file, deployed on its own) decide what any given signed-in user is actually allowed to do. This matters: it means access control can't be bypassed by editing the app's own code, only by changing the rules themselves.

03 The data model

CollectionHoldsWho can read it
sotw_profilesName, email, role (owner / admin / member) for every teammateEveryone signed in

sotw_myvoteEach person's own current vote — one document per voterOnly that person

sotw_payout_requestsPending / approved / rejected cash-out requestsRequester, admin, finance
sotw_payoutsPermanent log of every bonus actually paid outAdmin, finance
sotw_balance_adjustmentsAudit trail for manual balance corrections — who changed what, from what, to whatAdmin, finance

Every collection name is prefixed sotw_ — a deliberate namespace so this app's data can share a Firestore project with something else later without colliding.

04 What the security model actually guarantees

✓

Vote privacy is enforced by the database, not the UI. Nobody — not even an admin — can read who voted for whom. Only anonymous per-candidate totals exist, and even those are hidden until the week is revealed.

✓

Money can't be minted from the browser console. Balance writes are constrained by type and direction at the database level — a finance holder can lower a balance, never raise one, regardless of what the app's UI shows.

✓

The weekly bonus pays out exactly once. Reveal and payout land in a single atomic operation, so a network hiccup can't leave someone marked as revealed without being paid, or paid twice.

✓

Every manual money change is logged. A balance correction from the team panel always writes a permanent record of who made it and what changed — there's no way to quietly adjust a number.

05 Shipping a change

Two independent deploy targets, kept deliberately separate:

# app code — UI, features, behavior firebase deploy --only hosting # security rules — who can read/write what in the database firebase deploy --only firestore:rules

Splitting these means a routine UI update can never accidentally loosen (or freeze) the security rules — that only ever happens as its own deliberate step.

06 Notable milestones

Rebuilt from a single-file legacy page

The original app was one large HTML file. It was rebuilt as a proper React + TypeScript codebase for maintainability — the legacy version is being retired.

Gate/auth screen redesign

The sign-in experience went through several iterations to a centered, glass-panel design on a dark backdrop.

Security audit and hardening pass

A full review of the Firestore rules found and closed several real gaps — including a way for any signed-in account to inflate vote counts, and a way for the finance role to raise balances instead of only lowering them.

Admin self-service pass

Team and finance management were hardened so routine operations — adding people, fixing a balance, recovering from a stuck state — never require a direct database edit.
